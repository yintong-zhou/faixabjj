# Login with a username — design

Date: 2026-09-29 · Status: approved in chat, awaiting spec review

## Intent

**Convenience.** Everybody keeps an email address (it stays required); a
username is a second, shorter way to sign in (`mario.rossi` instead of the full
address). It is **not** for members without an email, nor for shared
addresses.

Decisions taken with the user:

| Question | Answer |
| --- | --- |
| Purpose | Convenience; email stays mandatory |
| Who chooses it | The maestro proposes it at creation; the person can change it from `/account` |
| Mandatory? | Yes for every account: new ones get it at creation, existing ones get one generated by the migration |
| Approach | `person.username`, resolved to the account's email on the server with the service role (A) |

Rejected approaches: a public SQL function `email_for_username()` (would let
anybody map usernames to emails); a synthetic email per username in Supabase
Auth (Auth has no aliases, so it would mean two accounts per person).

## Rules

- **Format** `^[a-z0-9._-]{3,30}$`: lower case only, no `@` — the login tells an
  email from a username by the `@` alone. Input is lower-cased and trimmed
  before it is checked, so case never matters to the reader.
- **Unique across the whole platform**, not per gym: at login the gym is not
  known yet.
- **Anti-enumeration** as for email: an unknown username and a wrong password
  give the same generic message.
- A **collision never becomes an error at creation**: the server appends a
  number (`mario.rossi2`, `3`, …) and the final username is shown with the
  temporary password.
- The platform superadmin has no `person` row and therefore no username; it
  signs in with its email only.
- Password recovery stays email only.

## 1. Database — `supabase/migrations/20260930000000_person_username.sql`

Replay-safe (runs twice cleanly).

1. `alter table public.person add column if not exists username text;`
   plus a check constraint (added only if missing) enforcing the format above.
2. Unique index on `username` (partial: `where username is not null`), global.
3. **Backfill** for rows that have an account (`auth_user_id is not null`) and
   no username, in `created_at` order: base = `lower(extensions.unaccent(full_name))`,
   whitespace → `.`, characters outside `[a-z0-9._-]` removed, repeated or
   edge dots trimmed, cut to 30 characters (leaving room for the suffix),
   `user` appended when shorter than 3; then the first free of `base`,
   `base2`, `base3`, …. Rows without an account get none — `restoreAccess`
   gives them one.
4. Redefine `public.guard_person_auth_link()` (last: `20260927000000`) with
   `username` added to `v_self_editable`, so a member may change their own
   username and nothing else new. The function body is otherwise restated
   verbatim.
5. Tests in `supabase/tests/tenant-isolation.sql`:
   - a username already used in another gym is refused (unique violation);
   - a member can change their own username, not another member's;
   - the check constraint refuses `@` and upper case.

`username` is added to the `select` lists that need it; `member_overview` is
**not** changed (the Registro does not search by username).

## 2. Login

- `/login`: the field becomes **"Email o username"** (three languages),
  `type="text"`, `autocomplete="username"`, name still `email`.
- `utils/login-identifier.ts` — pure, unit-tested:
  `parseLoginIdentifier(raw)` → `{ kind: "email", email }` |
  `{ kind: "username", username }` | `{ kind: "invalid" }`
  (contains `@` → email; otherwise lower-cased, trimmed, format-checked).
- `utils/supabase/login-identifier.ts` (`server-only`):
  `emailForUsername(username)` — service-role client, finds the `person` row
  with that username and a linked account, then `auth.admin.getUserById` for
  the **account's** email (the row's `email` may differ). Returns the email or
  `null`; never reaches the browser.
- `login/actions.ts`: resolve the identifier first. When it is a username that
  resolves to nothing, is invalid, or the secret key is missing, still call
  `signInWithPassword` with a fresh random non-existent address per
  attempt (`nobody-<uuid>@faixabjj.invalid`; a fixed one could be registered), so the reply is the same generic message and
  Turnstile is verified and consumed exactly as for a real attempt. Failures of
  the lookup are logged with `logDbError`, never shown.

## 3. Interface

- **`/members/new`** — required **Username** field, pre-filled from the name as
  it is typed (`Mario Rossi` → `mario.rossi`) until the maestro edits it;
  suggestion from `suggestUsername(fullName)` in `utils/username.ts` (pure,
  tested, same rule as the migration, reusing `foldForSearch()`).
- **Server, one helper** `claimUsername(admin, personId, wanted)` in
  `utils/supabase/username.ts` (`server-only`): validates the format, then
  writes the first free of `wanted`, `wanted2`, … to the row with the service
  role, retrying on unique violation (at most 50 tries); returns the
  username it got. Used by `addPerson`, `addManager` (`/gyms`, field on the
  manager form too) and `restoreAccess` (suggestion from the name when the row
  has none). A failure after the account exists is reported like today's
  "account created, profile not saved" case.
- **Temporary password notice** — "Username **mario.rossi2** · password
  **xxxx-xxxx-xxxx**", shown once; `TemporaryPasswordFlash` gains `username`.
  `setTemporaryPassword` / `resetManagerPassword` show the existing username too.
- **`/account`** — the person sees their username and can change it in the
  profile form (own client, RLS + the extended allowlist). Messages: "Username
  già in uso" on unique violation, a format explanation on a check violation.
- **`/members/[id]`** — username shown read-only next to the email.
- All strings in `it.ts` (authoring), `en.ts`, `pt-BR.ts`.

## Testing

- Vitest: `parseLoginIdentifier`, `suggestUsername` (accents, spaces, symbols,
  too short, too long).
- Docker replay twice + `--isolation` with the new tests.
- In the app: create a person and read the notice; sign in with the username
  and with the email; wrong username vs wrong password give the same message;
  change the username from `/account`, including a taken one.
